# BioVeracity — Environmental Evidence Intelligence Platform

## Overview
Environmental evidence intelligence platform — "What happened? There should only be one answer." Connects physical measurements, operations, weather, regulatory records, planning, human experience, and management action into one defensible chronology.

## Design System
- **Palette**: Dark navy background (HSL 224 35% 7%), amber accent (HSL 42 78% 55%), light foreground
- **Typography**: DM Sans body, Plus Jakarta Sans display, JetBrains Mono data/code
- **Style**: Bloomberg/Reuters/FT data journalism aesthetic — institutional, professional, not green/sustainability cliché
- **Default theme**: Dark mode

## Evidence Taxonomy (core system)
- ● Verified Record (R/P) — green — regulator or statutory evidence
- ◐ Corroborated Report (G/O) — amber — government or operator records
- ○ Unverified Report (C/M) — gray — community or media reports
- △ BioVeracity Inference (A) — blue — analytical inference

## Data Architecture
- PostgreSQL with Prisma ORM
- Assets, Events, Authorisations, CapitalProjects, RegulatoryActivity, Measurements, CommunityReports, NewsItems, EvidenceGaps, Watchlists, Leads, Questions
- All intelligence sourced from /home/ubuntu/bioveracity_market_intelligence.md

## Key Pages
- `/` — Homepage with hero, live intelligence feed, categories, priority assets, method, trust statement
- `/ask` — Streaming LLM-powered Q&A with structured answer format
- `/asset/[slug]` — Detailed asset pages with 9 tabbed sections
- `/assets` — Filterable asset grid
- `/regions/[slug]` — Regional pages (irish-ports, cambridgeshire, scotland, northern-ireland)
- `/lead` — "Bring Us A Live Problem" form
- `/login`, `/signup` — Auth pages

## MAJOR PRODUCT PIVOT (v2 — Universal Environmental Memory)

The product is being re-architected from persona/asset landing pages into ONE universal place-centric "environmental memory". Core thesis: "The environment doesn't have a data problem. It has a memory problem."

### The Product in 7 actions (the core loop — Phase One)
SEARCH IT → SEE IT → REWIND IT → SEE WHERE IT CHANGED → ASK IT → FOLLOW IT → PRODUCE THE PDF

### Non-negotiable UX rules
- ONE product for ALL personas (fisherman → national institution). Personas differ only in SCOPE/SCALE, never in interface. No persona-specific products, no four-door sales funnel.
- Homepage = ONE dominant search: "What do you want to understand?" with rotating example placeholders (River Blackwater, Lough Neagh, Port of Cork, wastewater near Cambridge...). NOT a conventional SaaS landing page. No "what industry/job title" gating.
- Universal Place Page (same structure for river/port/lake/wastewater/factory/catchment): Overview / Timeline / Evidence / Map / Ask BioVeracity / [Produce PDF] + [+ Follow].
- Chronology is the heart. Time slider = "rewind the environment" (years→months→days→hours ONLY where evidence resolution supports it — never fabricate temporal precision).
- Never sell complexity. Say "See what happened", "The evidence starts to disagree here", "Follow this place", "Produce PDF", "Ask BioVeracity" — never RAG/LLM/graph/vector/etc.
- Mobile-first: full loop must work on a phone beside a river with no instruction.
- Visual language: FlightRadar24 × FT data desk × Google Earth × forensic timeline, but SIMPLER and CALM. Avoid SaaS dashboards, purple gradients, glossy cards, stock photos, fake stats.

### Evidence taxonomy (v2 — 5 states)
● VERIFIED RECORD | ◐ OFFICIAL/OPERATOR STATEMENT | ○ PUBLIC/COMMUNITY REPORT | △ BIOVERACITY ANALYSIS | □ EVIDENCE GAP
Every item clickable to source where possible. UNKNOWN = UNKNOWN.

### Divergence Engine (core differentiator)
Detect where previously compatible evidence streams begin to tell materially different stories. Timeline states: ● event, ▲ material change, ⚠ evidence divergence, ✓ corroboration, □ evidence gap. Contradiction view: What official record said vs what other evidence showed / first divergence date / what happened next / status (resolved/partial/unresolved/insufficient). NEVER manufacture an anomaly where evidence doesn't support one — state "No material divergence identified."

### Observation → Signal → Event → Attribution
Never collapse stages. Complaint ≠ proof. Correlation ≠ causation. Absence of evidence ≠ evidence of absence.

### Accounts & data capture
Public discovery is genuinely useful (don't cripple it). Account required only for continuity: Follow, Save, My Places, alerts, PDF. Signup = email+name+password/magic-link only, return user to exactly where they were. Progressive/consent-aware data capture via explicit actions + ONE optional "Why does this place matter to you?" question. Never re-ask what actions already reveal.

### Commercial (no funnel)
No public pricing. When needs exceed personal use show "Request Institutional Access". Access states: PUBLIC / REGISTERED / DEMO / INSTITUTIONAL / ADMIN. Demo access is admin-managed (never hardcode individuals). My Places (personal) = Operating Picture (institutional) — same architecture, different scale.

### Later phases
P2 data breadth (rivers/lakes/catchments/wastewater/ports/maritime/industrial + UK+IRL jurisdiction normalisation). P3 alerts/saved searches/operating pictures/analytics. P4 demo+admin+institutional+evidence rooms. P5 intervention tracking/proof-of-effect/sensors. Sensors NEVER lead — they appear only when chronology identifies an evidence gap.

### Map
Default to keyless Leaflet + OpenStreetMap for the loop. Google Maps Platform (needs paid API key) is an optional upgrade — do not block the loop on it. Never present Google Air Quality API as an H2S/NH3/VOC sensor.

## v6 — Direct machine-to-machine ingest endpoint (COMPLETE, checkpointed "Direct Grok ingest endpoint + admin monitor", NOT deployed)

Replaces email-based ingestion. Grok Bot / BioVeracity Scout POSTs schema 2.1 JSON directly → app stores it → DB remembers → app reads DB. No manual seeding / no copying JSON into source.

### Endpoint — `POST /api/ingest/grok` (`app/api/ingest/grok/route.ts`, force-dynamic)
- Auth: header `X-BioVeracity-Ingest-Key` compared to env `BIOVERACITY_INGEST_KEY` (set in .env, generated random `bv_ingest_<48hex>`; value stashed in /tmp/_ingestkey.txt, never printed in chat). Invalid/missing → 401. Key never sent to browser.
- Body parse fail → 400. Zod validation (`lib/ingest/schema-2-1.ts` `schema21`) fail → 400 with issues.
- Deterministic fingerprint = sha256 of recursively key-sorted JSON (order-independent). Duplicate fingerprint → 200 `{success:true,duplicate:true,rawIngestId}`, increments `RawIngest.duplicateHits`, never re-ingests. P2002 race handled same way.
- Raw-first: stores full payload in RawIngest (status FOUND, foundAt) BEFORE interpreting.
- Interpretation: one ObservationCandidate per observations[] item (candidates, NOT public Events; coordinates_proposal/confidence_proposal are proposals only; EDM metrics stored verbatim, never interpreted as damage). CommercialSignal stored SEPARATELY. entity_resolution_proposals → EntityCandidate (matched via resolveAsset or UNRESOLVED). analysis stored on RawIngest.analysis (proposals, never auto-published). Then status→PARSED,parsedAt. Success 200 `{success:true,rawIngestId,observationsReceived,status:"PARSED"}`. Interpretation error → status FAILED,failedAt,error, 500 (raw preserved). GET → 405.

### Schema (prisma, all ADDITIVE, db push done safely): `RawIngest`, `ObservationCandidate`, `CommercialSignal`, `EntityCandidate`. RawIngest has per-state timestamps foundAt/parsedAt/verificationPendingAt/verifiedAt/normalisedAt/publishedAt/failedAt for pipeline FOUND→PARSED→VERIFICATION_PENDING→VERIFIED→NORMALISED→PUBLISHED / FAILED. duplicateHits Int counter. Cascade delete children.

### Entity resolution (`lib/ingest/resolve.ts`): CONSERVATIVE — exact slug (findUnique) or exact case-insensitive name/identifier/alias (findFirst) match against Asset ONLY. Returns assetId or null.
